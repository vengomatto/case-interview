Deploy to Kubernetes
without learning Kubernetes

A golden path for a team that has never used Kubernetes: one file in the team's repository, a pipeline that builds and verifies, a pull request that releases, and a platform that owns everything else.

Works today: runs and was verified Planned: specified, not built To explore: needs a spike first

The team owns one file

The setup form creates it from five answers; the team edits it later. Names, images, ports and paths: no Deployments, probes, quotas or network rules.

# deploy/service.yaml  (in the team's own repo)
name: testkube-sample
host: testkube-sample.localhost
components:
  api: {image: ghcr.io/org/api, tag: <set by CI>, port: 8080, path: /api}
  web: {image: ghcr.io/org/web, tag: <set by CI>, port: 4173, path: /}
database: {enabled: true}
smoke:
  - {component: api, path: /hello-pg, contains: "hello world"}

The platform turns it into about 20 objects

  • Namespace, quota, network rules
  • Deployments, Services, Ingress
  • Database with storage
  • A smoke test after every release

A schema rejects anything outside the contract, and teams cannot override the platform's settings.

What we assumed

Most of these come with the brief. Each one is written down so nobody has to guess.

The brief
  • Kubernetes is required.
  • The team does not know it, and should not have to.
  • A local cluster stands in for a cloud cluster.
The services
  • Web applications with a Dockerfile, one port and a health URL.
  • Postgres is the only database: in the cluster here, as the sample does, and managed in production. The application creates its own schema when it starts.
  • GitHub holds the code and runs the pipeline.
The people and the plan
  • Developers use GitHub and a browser, not kubectl.
  • Everything lives in Git: changes are reviewed and revertable, and the screens only show.
  • One team starts; a platform team owns the chart.
  • Separate concerns: product teams own what runs, the platform owns how it runs. The file and the pull request flow are the stable contract between them.
  • Security starts with a baseline (non-root, limits, network rules) and grows after the first deploy.

Environments: our position

Today there is one environment; the target is two, and they are enough here. A preview answers "does this change work" before the merge. Production is reached directly after it, with a revert one click away.

Many, short-lived

Preview

Does this change work?

  • One per branch or pull request
  • Own URL and data
  • Gone when the work ends
One

Production

Real users.

  • Reached after the merge, by the same pipeline
  • Rolling update and a smoke test
  • Revert to roll back
Without a staging, canaries matter more. A staging and a canary answer the same question, "is the merged result safe?": the first before production, the second inside it. A canary needs real traffic and per-version metrics, so it is the next investment once those exist, not something we have.
A. Previews and productionSimple, fast, one clear path. Our position.
B. Add a shared stagingFor risky database migrations, many services, or a required sign-off before production.
C. A dedicated staging clusterAlso to rehearse platform upgrades. A second cluster, DNS and data to run.
D. Canary in productionReplaces much of a staging. Needs metrics and traffic.

When something is red: no kubectl Works today

The developer answers three questions: what failed, where, and what to do. In GitHub and the Argo CD screen.

1. Pipeline red?Open the failing step: test, build or verify images.
2. Deploy PR open?The repository wants an approval. Approve and merge it.
3. Not Synced?Argo CD shows the chart or values error on the application.
4. Not Healthy?Click the red pod: the Logs and Events tabs say why.
5. Smoke test red?The job log names the failing request. Roll back.
Seen here: a crash on a read-only folder, a 404 caused by an earlier step not being ready, a permanent "out of sync". Missing: a read-only role for developers, logs that survive a crashed pod, alerts.

Known limits, stated up front

  • One environment only. Previews are designed; a staging is not planned.
  • Creating a service has manual steps: the repository settings, the registration pull request and the image pull secret.
  • Rollback, self-healing and a failed release follow from the design and the runbook but were not demonstrated live. NetworkPolicy enforcement on kind is unverified.
  • Previews are described one service at a time. Testing several services together is an open question.
  • The demo copies a personal token into the cluster. A real setup uses a GitHub App, a secret store and per-service IAM roles.
  • Security and robustness come after the first deploy, with a plan: scanning, signing, policy, backups.
  • The sample app has findings of its own (hardcoded database password, no health endpoint). They go back to its team.
